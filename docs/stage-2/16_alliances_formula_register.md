## 1. How to Read a Formula

Each entry in this register documents:
- **Formula ID:** Standard identifier `F-AL-###`.
- **Purpose:** Gameplay and economic justification.
- **Definition:** Exact mathematical expression using clean LaTeX notation.
- **Variables & Units:** Input definitions, types, and units.
- **Range & Bounds:** Valid boundary conditions and clamping rules.
- **Rounding:** Explicit truncation or ceiling rules.
- **Timing:** When the calculation executes within the turn lifecycle.
- **Edge Cases:** Boundary conditions (e.g. zero members, pool exhaustion).
- **Source Rules & Requirements:** Traceability to `ALL-###`, `REQ-###`, and `D-###`.
- **Decision Status:** Candidate Proposal or Owner-Reserved with dependency references (`UD-040`, `UD-043`, `UD-044`, `UD-046`). No formula in this register is Approved.
- **Worked Example:** Illustrative calculation walk-through; the numbers demonstrate the arithmetic and do not state policy.
- **Validation Expectation:** Test criteria for Prompt 09C and Prompt 14. A validator may test that the formula is labelled candidate, that its authority link exists, and that it is not presented as approved or enforced — **never** that a particular threshold is present.

### F-AL-001 — Dedicated Alliance Treasury Pool Storage Capacity

| Field | Definition |
|---|---|
| **Purpose** | Establish a candidate dedicated, bounded storage capacity for each resource pool within an Alliance Treasury, ensuring economic isolation from national warehouse limits (`REQ-141`, `REQ-142`, `AX-08`, `UD-046`). |
| **Definition** | For each supported resource $R \in \text{SupportedResources}$:<br>$$\text{PoolCapacity}(R) = \text{BaseAllianceCapacity}(R) + \left(\text{MemberCapacityBonus}(R) \times N_{\text{active\_members}}\right)$$ |
| **Variables** | • $R$: Resource type (Crowns, Energy, Minerals, Manufacturing, Agriculture).<br>• $\text{BaseAllianceCapacity}(R)$: Baseline storage capacity granted to any active alliance. Unit: resource units (integer).<br>• $\text{MemberCapacityBonus}(R)$: Additional storage capacity scaled per active member. Unit: resource units / member (integer).<br>• $N_{\text{active\_members}}$: Count of members with status `ACTIVE_MEMBER` at calculation turn. Unit: members (integer). |
| **Range** | • For Crowns: $\text{BaseAllianceCapacity}(\text{Crowns}) = 1,000,000$; $\text{MemberCapacityBonus}(\text{Crowns}) = 100,000$. Range: $[1,000,000, 100,000,000]$.<br>• For Physical Commodities: $\text{BaseAllianceCapacity}(R) = 50,000$; $\text{MemberCapacityBonus}(R) = 5,000$. Range: $[50,000, 5,000,000]$. |
| **Bounds** | Upper bound clamped at maximum configuration cap ($100 \times \text{BaseAllianceCapacity}$). Minimum bound clamped at $\text{BaseAllianceCapacity}(R)$ even if $N_{\text{active\_members}} = 0$. |
| **Rounding** | Strict integer arithmetic. No fractions. |
| **Timing** | Re-evaluated dynamically upon member admission, departure, or expulsion; evaluated at phase P2 prior to deposit processing. |
| **Edge Cases** | • *Member leaves while pool is full:* The candidate model would decrease capacity into an `OVER_CAPACITY` state, with no resources lost or destroyed and further deposits blocked until the balance drops below capacity (`ALL-105`). No such block exists while `UD-046` is open.<br>• *Zero members:* Base capacity remains intact during grace period before automated dissolution. |
| **Source** | `ALL-104`, `ALL-105`, `REQ-176`, `REQ-572`, `AX-08`. |
| **Decision Status** | **Candidate Architectural Proposal — Capacity Model and Parameters Awaiting Owner Decision UD-046 (Unapproved). Preserves the binding inherited REQ-176 non-minting invariant (Provisional requirement).** |
| **Example** | An alliance has $N = 10$ active members. For Iron:<br>$$\text{PoolCapacity}(\text{Iron}) = 50,000 + (5,000 \times 10) = 100,000\text{ units}$$<br>If current Iron pool holds $98,000$ units, a deposit of $3,000$ Iron would exceed $100,000$ and is rejected cleanly with `ALF-02`. |
| **Validation** | Prompt 09C: Test deposit acceptance below capacity, clean rejection above capacity, capacity recalculation on member exit, and non-destruction of over-capacity stored balances. Prompt 14: Economic load testing. |
| **Value** | **Base 50,000 / Bonus 5,000 per member — Candidate Proposal (Category D / Category C Provisional Baseline pending UD-046 / Prompt 14 calibration).** |

### F-AL-005 — Treasury Multi-Signature Dual Authorization Threshold

| Field | Definition |
|---|---|
| **Purpose** | Prevent single-actor embezzlement, rogue officer looting, or compromised credential draining of pooled alliance resources (`ALL-109`, `ALL-110`, `AX-07`, `R-AL-01`, `UD-046`). |
| **Definition** | A withdrawal proposal requires two distinct player sign-offs (`PROPOSE_WITHDRAWAL` + `APPROVE_WITHDRAWAL` by different accounts) if:<br>$$\left(\text{Amount}(\text{Crowns}) > \text{Threshold}_{\text{Crowns}}\right) \lor \left(\frac{\text{Amount}(R)}{\text{PoolBalance}(R)} > \text{Threshold}_{\text{Ratio}}\right)$$<br>Where baseline defaults are proposed as:<br>$$\text{Threshold}_{\text{Crowns}} = 50,000\text{ Crowns},\quad \text{Threshold}_{\text{Ratio}} = 0.10\text{ (10\% of active pool)}$$ |
| **Variables** | • $\text{Amount}(R)$: Quantity of resource requested in withdrawal (integer).<br>• $\text{PoolBalance}(R)$: Total unreserved quantity of resource in alliance pool at proposal creation (integer).<br>• $\text{Threshold}_{\text{Crowns}}$: Absolute currency trigger threshold (integer).<br>• $\text{Threshold}_{\text{Ratio}}$: Percentage trigger threshold (rational fraction / basis points). |
| **Range** | • Currency: $[10,000, 500,000]$ crowns. Default baseline: $50,000$ crowns.<br>• Resource Ratio: $[0.05, 0.25]$ ($5\%$ to $25\%$). Default baseline: $0.10$ ($10\%$). |
| **Bounds** | Under the candidate model, a withdrawal below threshold would need only single-officer execution where single approval is configured, and one meeting or exceeding either condition would require dual authorization; self-approval would be prohibited (`ALL-111`). None of this is enforced today. Alliances could configure stricter thresholds if the mechanism is approved. The values `50,000` and `10%` are illustrative examples only and are not required by any validator or release condition. |
| **Rounding** | Ratio check evaluated via cross-multiplication: $\text{Amount}(R) \times 10 > \text{PoolBalance}(R)$. Strict integer logic. |
| **Timing** | Evaluated at proposal creation time (Phase 1) and re-verified at execution time (Phase 2). |
| **Edge Cases** | • *Pool balance decreases while a proposal is pending:* The candidate model re-evaluates the ratio at execution and would require a second sign-off if newly triggered.<br>• *Officer attempts to approve own proposal:* The candidate model would fail with `ALF-07` (`SELF_APPROVAL_PROHIBITED`). No such rejection is in force. |
| **Source** | `ALL-109`, `ALL-110`, `ALL-111`, `REQ-574`, `AX-07`, `D-136`, `UD-046`. |
| **Decision Status** | **Candidate Proposal — Treasury Dual Authorization / Multi-Signature Architecture and Thresholds Awaiting Owner Decision UD-046 (Unapproved). Preserves the binding inherited REQ-176 non-minting invariant (Provisional requirement).** |
| **Example** | Alliance Iron pool holds $200,000$ units. Officer proposes withdrawal of $25,000$ units to Member X.<br>$$\frac{25,000}{200,000} = 0.125 > 0.10$$<br>Because $12.5\% > 10\%$, the proposal triggers multi-sig. A second distinct authorized officer must approve before the withdrawal can execute. |
| **Validation** | Prompt 09C: Test sub-threshold single approval, threshold dual approval, self-approval rejection, pool depletion edge cases. |
| **Value** | **50,000 Crowns / 10% Pool Balance — Candidate Proposal (Category D / Category C Provisional Baseline pending UD-046 / Prompt 14 calibration).** |

### F-AL-006 — Automatic Per-Turn Production Tax Arithmetic

| Field | Definition |
|---|---|
| **Purpose** | Define the exact integer arithmetic by which an alliance collects tax automatically from each member nation's **current-turn production**, using that Alliance's frozen per-Alliance bracket assignment and separate Crowns and resource rates. The formula supplies no rate, bracket, assignment or office; those are player-defined under `ALL-181`–`ALL-184` and controlled by role permissions under `ALL-183`. It exists so `AX-27` has one deterministic computation and no engine-invented value (`REQ-618`–`REQ-625`, `ALL-179`–`ALL-187`, `D-140`). |
| **Definition** | For an active member $N$ at turn $t$, let the frozen snapshot $S_t$ supply, for each Alliance $A \in E(N,t)$, a per-Alliance bracket assignment $b_A(N,t)$ and bracket version $v_A$. An assignment belongs to exactly one Alliance; a bracket in Alliance $A$ is not a bracket in Alliance $B$. Let $\mathcal{A} = \{\text{Crowns}\} \cup \text{TaxableResources}$. $E(N,t)$ is the set of active alliances for $N$ at $S_t$ that could assert a tax claim. The applicable Alliance and rate are determinate only when $|E(N,t)| = 1$; if $|E| = 0$ the alliance tax is zero, and if $|E| > 1$ or the applicable claim cannot be established unambiguously the provisional multiple-membership safeguard sets $r_{A,a} = 0$ for every asset in that turn and records the reason. The safeguard creates no priority, is reversible and does not resolve `UD-040`. For that single applicable Alliance $A$, for each asset $a \in \mathcal{A}$, production can arrive in one or more production events during the turn. Let those events be indexed $j = 1,\ldots,m_a$ in the deterministic P3 settlement order, each with integer gross $g_{a,j}(N,t) \ge 0$, and let the cumulative gross be $C_{a,j} = \sum_{k=1}^{j} g_{a,k}$. Set $D_{a,0} = 0$ and define the cumulative tax due and the tax at each event as:<br>$$C_{a,j} = \sum_{k=1}^{j} g_{a,k},\qquad D_{a,j} = \left\lfloor \frac{C_{a,j} \times r_{A,a}(v_A)}{10{,}000} \right\rfloor$$<br>$$\text{TaxAlreadyCollected}_{a,j-1} = D_{a,j-1},\qquad \text{TaxDueAtEvent}_{a,j} = D_{a,j} - D_{a,j-1}$$<br>$$\text{TaxAtEvent}_{a,j} = \text{TaxDueAtEvent}_{a,j},\qquad \text{NetAtEvent}_{a,j} = g_{a,j} - \text{TaxAtEvent}_{a,j}$$<br>At the end of the turn, with $G_a = C_{a,m_a}$:<br>$$\text{Tax}_{A,a}(N,t) = D_{a,m_a} = \left\lfloor \frac{G_a(N,t) \times r_{A,a}(v_A)}{10{,}000} \right\rfloor,\qquad \text{Net}_a(N,t) = G_a(N,t) - \text{Tax}_{A,a}(N,t)$$<br>The per-event deduction is therefore the increment of the floored cumulative liability, never an independent floor of each event: $\sum_{j=1}^{m_a} \text{TaxAtEvent}_{a,j} = D_{a,m_a}$. A single-event asset, including Crowns in P3.1, uses $m_a = 1$, so its event tax equals the end-of-turn tax. $G_a$ is **gross eligible production of asset $a$ during turn $t$ only** and $r_{A,a}(v_A)$ is the bracket version's rate for that asset in integer basis points. Different assets keep separate accumulators; no gross, tax or fractional remainder is transferred between assets. The Alliance Receiving Ledger credit is: $$\text{ARL}_{A,a}(t) = \sum_{N \in \text{ActiveMembers}_A(S_t)} \text{Tax}_{A,a}(N,t)$$<br>Eligibility is a separate boolean: $$\text{TaxableMember}_A(N,t) = \text{ActiveMember}_A(N,S_t) \land \text{AttributionDeterminate}(N,t)$$<br>If $N$ is not an active member of $A$ at the snapshot, every $\text{Tax}_{A,a} = 0$; non-members are never taxed. If $N$ is active but has no valid assignment in $A$, a deleted or invalid assignment, or an unconfigured asset rate, the explicit 0% fallback bracket supplies $r_{A,a} = 0$ and the receipt records the fallback; that fallback never borrows a bracket from another Alliance. If $N$ is active in more than one alliance, or its applicable alliance cannot be established unambiguously, the multiple-membership safeguard also supplies $r_{A,a} = 0$, records the reason and leaves gross production intact. Collection is at the production source: Crowns after the P3.1 `TAX_INCOME` event; each resource at its P3.3 extraction or P3.5 processing production event, before any later P3 consumption. Later same-turn stages may consume only $\text{Net}_a(N,t)$; the taxed amount is not available to the nation in that turn, an existing stockpile is not taxed when consumed later, and a processing input is not taxed again. |
| **Variables & Units** | • $g_{a,j}(N,t)$: integer gross production of asset $a$ at production event $j$ during turn $t$, before alliance tax and before later same-turn P3 consumption; $g_{a,j} \ge 0$.<br>• $m_a$: number of production events for asset $a$ in the turn, in deterministic P3 settlement order; $m_{\text{Crowns}} = 1$ because P3.1 credits Crowns income once, while a stored resource may have $m_a \ge 1$ where a later P3 stage creates the same asset more than once.<br>• $C_{a,j} = \sum_{k=1}^{j} g_{a,k}$: cumulative gross production of asset $a$ through event $j$; $C_{a,0} = 0$ and $C_{a,m_a} = G_a$ for the turn.<br>• $D_{a,j} = \lfloor C_{a,j} \times r_{A,a} / 10{,}000 \rfloor$: cumulative tax due through event $j$; $D_{a,0} = 0$ and $D_{a,m_a} = \text{Tax}_{A,a}(N,t)$.<br>• $\text{TaxAlreadyCollected}_{a,j-1} = D_{a,j-1}$: tax already deducted for asset $a$ earlier in the same turn, which is exactly the prior cumulative tax due.<br>• $G_{\text{Crowns}}(N,t)$: gross national tax income for the turn as computed and credited by B-04 `ECN-094`/`ECN-146` in P3.1, **before** alliance tax (integer crowns).<br>• $G_R(N,t)$: gross output of supported stored resource $R$ classified by B-04 as production in P3.3 extraction or P3.5 processing during turn $t$, **before** alliance tax and before any same-turn P3 consumption (integer units).<br>• $r_{A,a}(v_A)$: Alliance $A$'s bracket-version asset rate in integer basis points, $0 \le r_{A,a} \le 10{,}000$ (integer; 1 bp = 0.01 percentage point).<br>• $b_A(N,t)$: the single active frozen bracket assignment for nation $N$ **in Alliance $A$** at snapshot $S_t$, or the explicit 0% fallback bracket. Each assignment identifies its Alliance.<br>• $S_t$: the immutable turn snapshot of membership, bracket versions, per-Alliance assignments and rate-setting permissions, with a recorded `snapshot_id`.<br>• $v_A$: Alliance $A$'s bracket version effective at $S_t$.<br>• $E(N,t)$: the set of active alliances for $N$ at $S_t$ that could assert a tax claim; collection is determinate only when $|E| = 1$.<br>• `attribution_status`: `single-alliance`, `no-alliance`, `ambiguous-multiple-membership-0%-fallback` or the applicable bracket fallback, recorded on the receipt. |
| **Range & Bounds** | Each $r_a$ is any integer from $0$ through $10{,}000$ inclusive: $0\%$ through $100\%$ inclusive. Rates are **not** restricted to multiples of 10% and no small option list exists; $37\%$, $55\%$, $73\%$, $1\%$ and $99.99\%$ are all representable (storage precision is 0.01 percentage point). No rate is supplied by the engine, the platform, an AI or a default: an absent, deleted, invalid or unassigned rate is $0$. Different members may hold different brackets and different assets may carry different rates. By construction $0 \le \text{TaxAtEvent}_{a,j} \le g_{a,j}$ for every event and $0 \le \text{Tax}_a \le G_a$ for the turn; the differences of a non-decreasing floored cumulative liability cannot be negative or exceed the event's gross. A 100% rate is valid and yields $\text{Net}_a = 0$. There is no per-event independent floor, so a turn with several small fractional events cannot under-collect relative to its total gross, and it cannot over-collect because each event's deduction is the increment of the same cumulative liability. |
| **Rounding** | One rule only: floor the **cumulative** tax due $D_{a,j} = \lfloor C_{a,j} \times r / 10{,}000 \rfloor$ to a whole unit using integer arithmetic, then subtract the already-collected cumulative amount. Never floor each event's product independently, because independent floors lose a fractional unit at every small event and under-collect the turn. Settlement debits the reservation and records the platform cost: $\text{Avl}=90{,}000$, $\text{Rsv}=0$, $\text{Exp}=10{,}000$; $\text{Rec}$ remains 100,000 and $90{,}000+0+10{,}000=100{,}000$. A retry returns the same receipt and applies zero. A second authorization for 95,000 fails with `ALF-28` because only 90,000 is `AVAILABLE`; no debt or negative balance is created. The numbers demonstrate accounting, not an approved fee or purpose. |
| **Validation Expectation** | Prompt 09C: test that no purpose is spendable while no cost schedule is approved; test the invariant after receipt, allocation, settlement, release and failure; valid and invalid purpose/schedule/amount/destination; authorized and unauthorized actor; insufficient `AVAILABLE`; `RESERVED` and `EXPENDED` non-spendability; no negative balance, debt or cross-asset substitution; retry and conflicting-key behaviour; at-most-once payment; no player recipient, distribution, grant, loan, refund or general withdrawal; no capacity rejection; reconciliation of every category to receipts and audit; Crowns and resource assets; and interaction with tax/donation credits. Prompt 14: calibrate a cost schedule only if the owner adopts one. |
