## 1. Scope and precedence

Two registers, two jobs:

| Register | Holds | Authority |
|---|---|---|
| [DECISIONS.md](../DECISIONS.md) (D-xxx) | Project-level decisions: continuity, stage pacing, name, hosting, closure, roadmap | The only place an **approval** is recorded |
| This file (DD-xxx) | How those decisions and the Stage 1 proposals translate into **design positions** the Bible will implement | Working register; never upgrades a status on its own |

**Precedence when they disagree:** DECISIONS.md wins. A `DD` row may summarise a `D` row but may not extend it.

**One rule that matters most:** nothing here becomes approved by being written down here. Promotion requires an entry in DECISIONS.md. D-003 and D-012 set that discipline, and D-014 says who may write the entry: the owner for fixed constraints, the working AI for ordinary design decisions, each with cited evidence.

## 4. How a status changes

| From → to | Requires |
|---|---|
| Provisional → Approved | A recorded entry in [DECISIONS.md](../DECISIONS.md) that cites this DD ID and the affected requirements. For a fixed constraint it is an owner decision; for an ordinary design decision it is made and recorded by the responsible Stage 2 prompt under [the policy](../AUTONOMOUS_DECISION_POLICY.md) (D-014) |
| Proposed → Provisional | A Stage 2 prompt that writes the rule into an authoritative subsystem document and labels it provisional |
| Any → Superseded | A newer entry that names the replaced one; the old row is kept |
| Deferred → active | The gate or stage named in the row is satisfied, with evidence |

**Forbidden:** a prompt declaring its own output approved; a document describing a provisional value as "the rule"; presenting a provisional Operations Points value as approved because the model (D-015) is.
