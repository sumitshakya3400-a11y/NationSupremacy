## 1. Blocking classes

| Class | Meaning | Test |
|---|---|---|
| **A — Blocking design decision** | The named prompt cannot produce a coherent rule without it | Would two competent designers write incompatible rules? |
| **B — Provisional design choice** | A documented candidate can carry the work, but approval may be needed before it is permanent | Can the prompt proceed with a labelled candidate? |
| **C — Playtesting / simulation item** | The rule can be specified; its balance needs evidence | Is the uncertainty numeric, not structural? |
| **D — Implementation-stage detail** | Behaviour can be defined now; the mechanism belongs later | Is the missing part technical, not design? |
| **E — Accepted carry-forward risk** | Understood, deferrable, does not make the design incoherent | Does the design still work if this stays open? |

A class is **scoped to its prompt**: UD-002 is class A for Prompt 07 and irrelevant to Prompt 02. No A-class item blocks Stage 2 from starting.

## 5. Resolution protocol

Resolutions made under [the autonomous decision policy](../AUTONOMOUS_DECISION_POLICY.md) cite the `D-` entry that records them; a resolved row is never deleted, and its original options remain visible as history.

**Status meanings used here (mutually exclusive):** **Resolved** — the design question has a recorded answer; **Deferred to Prompt NN** — the remaining rule is intentionally assigned to a named future prompt and is **not** resolved; **Open** — the answer genuinely needs evidence, a measurement, or a legal decision that does not yet exist. "Awaiting validation" is not a fourth row status: it is a separate proof condition on an otherwise resolved decision (for example UD-016/CF-02).

When a prompt resolves an item it must: change **Status** to `Resolved`, name the authoritative document and section, cite the evidence (decision entry, simulation, or owner answer), and keep the original question text. If a resolution is later reversed, the row becomes `Superseded` with a link to the successor — never deleted.

Unresolved items are re-checked at Prompt 15. An item may be carried out of Stage 2 only with a class, an owner and a destination stage.

**"Owner approval" under D-014.** The column answers one question only: *does this row need a person outside the project?* Since [the policy](../AUTONOMOUS_DECISION_POLICY.md) took effect, ordinary game, UX, formula and documentation decisions are resolved and recorded by the responsible prompt. That policy does **not** override an owner reservation. **UD-040…UD-049 are owner-reserved decisions**: assigning a row to a prompt, preparing a candidate, recording a narrow authorization or documenting a partial decision resolves only the exact portion the owner authorized. It does not resolve the remainder, does not transfer the reserved choice to a prompt and does not convert the row into ordinary prompt work. The unauthorised remainder stays Open and keeps its owner-decision position. **UD-017** (which jurisdiction's data-protection law applies) is separately a genuine Category D item, because it is a legal position the project cannot self-assign. Every `No — Prompt NN decides` cell outside the owner-reserved set means the owning prompt must settle it there, with a `D-` entry and an update to the authoritative rule — not that it may be carried indefinitely.
