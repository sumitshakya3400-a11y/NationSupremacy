**Stage:** Stage 2 · **Parent:** Prompt 14 · **Subphase:** 14A · **Created:** 2026-11-13  
**Status:** Inventory and ownership map only. No value is changed, approved or calibrated here. The owning register remains authoritative.

**Record count:** **393 parameter inventory records** — 7 B-02, 20 B-03 and 366 across B-04…B-12. Some records represent vectors or grouped numerical values; 393 is a record count, not a scalar-value count.

## 1. Scope and method

This map records every **numerical design parameter** discoverable in the nine formula registers and in the B-02/B-03 rules that feed them. A numerical design parameter is a value the design chooses, caps, floors, prices, rates, thresholds, windows, fees, weights or provisional constants — not a player-supplied input and not a data-dependent variable.

Coverage is layered:

1. Every constant-table row in B-04 §3, B-05 §3, B-06 §3 and B-07 §3.
2. Every formula-level provisional value set in B-08, B-09, B-10 and B-11, where the register states the value inside the formula entry rather than in a separate table.
3. Every registered B-12 parameter `FP-P01`…`FP-P14`.
4. All 20 B-03 §21.2 carry-in parameters, reconciled in §4.
5. The B-02 timing conversions and phase constants in §3.

Where a parameter already has an identifier, that identifier is used unchanged. Where none exists, the row says `None` and uses the source's exact name; **no competing global namespace is invented**.

## 2. Ownership model

Five roles are kept distinct, because they routinely belong to different owners:

| Role | What it means |
|---|---|
| System rule owner | The register or prompt that defines the rule the parameter serves. |
| Numerical decision authority | Who may decide or approve the value. This is the field that matters for calibration. |
| Implementation owner | The later stage that must implement the parameter (Stage 5/6). It does not decide the value. |
| Validator / test owner | Who tests the parameter. Testing never transfers decision authority. |
| Owner-reserved | A value reserved to the project owner; the working AI may not set it. |

A parameter described in B-03, validated by Prompt 14 and implemented in Stage 6 remains owned by whoever B-03 names. Prompt 14 does not acquire ownership by testing.

## 16. Parameter-level findings

1. **The fair-value band has two sources.** B-03 §21.2 leaves it unspecified; B-07 and D-114 fix it at 3,000 bp. The B-07 value is a confirmed design rule but is **not** an owner-approved numerical value. Any calibration must update B-07 and re-cite B-03.
2. **`W_fresh` and the B-03 fresh-nation window are the same parameter** (`360` turns). The B-07 register names it `W_fresh`; B-03 names the rule. The values agree; the map records one parameter with two sources.
3. **The OP cap is provisional at 10** and is a paired parameter with the regeneration rate (`F-WR-001`). Calibrating one without the other is invalid.
4. **B-04's starting bundle is a vector of 24 values** approved in structure by D-063 but explicitly provisional in every number. It is not owner-approved.
5. **B-06's election cycle is fixed at 240 turns by D-107**, but the surrounding constants (campaign window, thresholds, penalties) remain provisional. The cycle value may not be changed by Prompt 14 without a new decision.
6. **B-12 has six undefined owner-reserved parameters.** No provisional value may be invented to make a formula executable; `UNSPECIFIED` is the correct state until the owner decides.

## 17. Maintenance rule

A change to any parameter requires: the owning register revision, this map's row, the affected formula inventory rows, and a re-run of the 14A validator. A calibration that changes a value without changing its row is a documentation defect.
